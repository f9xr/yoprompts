Agent context files

DESIGN.md & AGENTS.md

Two files that stop a coding agent from guessing. AGENTS.md says how to work in the repository: the commands, the conventions, the paths to leave alone. DESIGN.md says what the product should look like, as tokens plus the reasoning behind them. Every entry here is published by the project itself, with its licence attached.

Pick the right file

One is about the work, the other about the look

The two formats are close enough to get confused and different enough that using the wrong one shows up immediately.

AGENTS.md

How to work here

Install and dev commands, the test runner, lint rules, naming, the directories that are off limits, and how pull requests are shaped. A repository usually keeps one at the root, and it is read at the start of every session, so a wrong command costs tokens on every task.

DESIGN.md

What it should look like

Colours, type, spacing, radii, elevation and component rules, as YAML tokens with prose that says what each one is for and what never to do. Google's open spec makes the format portable between agents and tools, which is why a file can be dropped into a different project unchanged.

Adopting one

Read it, then make it yours

Step 1

Start from a file that fits

Copy the closest one into your repository root. An AGENTS.md written for a large Python monorepo will be wrong for a two-file TypeScript app, but its structure usually travels.

Step 2

Delete what does not apply

Every line you leave in is an instruction the agent will follow on every task. Keep the commands, the boundaries and the conventions, and cut the sections that describe a project you do not have.

Step 3

Check the licence

The licence is shown on every entry. MIT and Apache-2.0 files can be copied and adapted with attribution; if a project publishes a file without one, link to it instead of copying it wholesale.
